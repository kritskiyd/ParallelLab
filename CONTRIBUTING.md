# Правила разработки

## Работа с требованиями

Работа начинается с реального Issue. Epic объединяет направление; PBI описывает пользовательскую ценность и критерии приёмки; Task реализует конкретную часть PBI. Используются метки `epic`, `pbi`, `task` и нативные Sub-issues. Независимые функции не объединяются ради удобства отчётности.

Приоритеты `P0`, `P1`, `P2` соответствуют MVP, Version 1, Version 2. Оценка PBI выбирается из 1, 2, 3, 5, 8, 13 Story Points. Это относительная трудоёмкость и неопределённость, а не часы. Epic и дочерние Task не получают отдельную оценку SP, чтобы не считать одну работу дважды. Суммы спринтов считаются только по PBI.

До начала работы обновляются поле проекта, метки, milestone и документация при изменении релиза, оценки или планового спринта. Назначение Assignee означает согласованное принятие работы; автоматически назначать всех на одного автора нельзя.

## Ветки

`main` хранит согласованное состояние. Разработка функции ведётся в `feature/<номер-issue>-<краткое-имя>`, исправление в `fix/<номер-issue>-<краткое-имя>`. Ветки создаются только под реальную работу. Автоматизированный помощник при создании собственной рабочей ветки использует префикс `codex/` и указывает связанный Issue.

Пример после появления реализации:

```sh
git switch main
git pull --ff-only
git switch -c feature/11-create-experiment
```

Это пример команды, а не подтверждение существования такой ветки. Force push в `main` и переписывание чужой истории не допускаются.

## Коммиты

Один коммит содержит связанное изменение. Сообщение: краткое действие с типом `feat:`, `fix:`, `docs:`, `test:` или `chore:`. В теле указывается `Refs #<номер>`. Секреты, токены, пользовательские вычислительные данные и локальные настройки в Git не попадают.

## Pull Request

В PR указываются связанный PBI/Task, результат, способ проверки и ограничения. Изменение интерфейса сопровождается скриншотами обеих существующих тем. Изменение вычислительной логики сопровождается проверкой корректности результата на известных данных.

`Refs #N` используется для частичной работы. `Closes #N` разрешён только тогда, когда PR действительно завершает весь Issue и все его критерии. Завершение одного Task не закрывает автоматически весь PBI или Epic. Epic закрывается после принятия всех дочерних PBI, а не после первого PR.

## Review и завершение

Проверяются границы изменения, требования, тесты, обработка ошибок и отсутствие секретов. При индивидуальной разработке самопроверка явно обозначается как самопроверка; нельзя утверждать, что независимый Code Review состоялся, если второго участника нет.

Для `Done` нужны выполненные критерии приёмки, проверки, отсутствие блокирующих дефектов, обновлённая документация и согласованный результат Review. Закрытие Issue и слияние PR не заменяют доказательства этих условий. Правила подробно описаны в [Scrum-процессе](docs/Scrum-Process.md).
