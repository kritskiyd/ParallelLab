# Организация Scrum

## Роли

Владелец продукта упорядочивает бэклог и проверяет ценность результата. Scrum-мастер помогает соблюдать процесс и устранять препятствия. Разработчики оценивают работу, выбирают объём спринта и создают проверенный результат. В учебном проекте Критский С. Д. может совмещать обязанности. Персоны не назначаются исполнителями, вымышленная команда не создаётся. Поле Assignees заполняется при фактическом принятии задачи.

## Материалы Scrum-проекта

Цель продукта: пользователь проводит воспроизводимый локальный эксперимент и корректно сопоставляет реализации. Бэклог состоит из реальных Issues: функциональный раздел → пользовательская история → техническая задача. Нативные родительские связи сохранены. Бэклог спринта включает выбранные истории, технические части и план достижения цели. Основное назначение находится в поле «Спринт». Работающий результат должен соответствовать условиям завершения; макет и описание задачи не заменяют реализацию.

## События

- Спринт: две недели, всего 13 предварительных интервалов. Цели, состав, зависимости и результаты указаны в [плане](Sprint-Planning.md).
- Планирование спринта: проверить зависимости, открытые вопросы, проверочные данные, доступность исполнителя и объём. Оценки не равны дням и не доказывают скорость команды.
- Ежедневное обсуждение: продвижение к цели, ближайший шаг и препятствия. При индивидуальной работе допустима краткая запись по фактической работе.
- Обзор спринта: демонстрация работающего сценария и свидетельств критериев, обратная связь и уточнение бэклога.
- Ретроспектива: анализ процесса и выбор конкретного улучшения.

Встречи здесь не объявляются уже проведёнными. Календарь корректируется с учётом загрузки и праздничных дней.

## Условия готовности задачи к разработке

Понятны роль, ценность и границы, есть конкретные требования, входы и выходы, сценарии и ошибки, проверяемые критерии, приоритет, выпуск, оценка и зависимости. Существенные открытые вопросы согласованы, проверочные данные определены. Размер позволяет завершить работу в спринте. Техническая часть имеет одного родителя и конкретный результат.

Задача с невыбранным CUDA-транслятором или несогласованной методикой замера не считается готовой автоматически. Назначение будущего спринта не переводит её в «Готово к работе».

## Условия завершения задачи

- Реализованы все согласованные критерии в пределах выпуска.
- Пройдены подходящие модульные, интеграционные и пользовательские проверки; вычисление проверено на эталоне.
- Ошибки и отмена обрабатываются явно, данные не теряются, нет блокирующих дефектов.
- Выполнена проверка кода или явно обозначенная самопроверка; результат принят ответственным за продукт.
- Документация и связи с Issue обновлены; изменения находятся в основной ветке, есть свидетельства проверок.

Функциональный раздел не закрывается по одной технической задаче или только по части первого выпуска: будущие дочерние функции остаются открытыми.

## Статусы и переходы

| Переход | Условие |
| --- | --- |
| Бэклог → Готово к работе | Подтверждены условия готовности и ближайший план |
| Готово к работе → В работе | Работа фактически начата |
| В работе → На проверке | Есть проверяемый результат, проверки и связь с изменениями |
| На проверке → Выполнено | Выполнены критерии, проверка и условия завершения |
| На проверке → В работе | Есть замечания для исправления |
| Выполнено → Бэклог | Issue переоткрыта, причина и критерии пересмотрены |

## Автоматизация

Восемь существующих правил переиспользованы; они используют те же поля и значения после переименования. Автодобавление ограничено Issues этого репозитория. Связанный запрос на слияние переводит Issue в работу, а не доказывает приёмку. `Closes #N` применяется только к полностью выполненной задаче, `Refs #N` используется для частичного вклада. Родительские истории не закрываются автоматически по одной дочерней задаче. Фиктивные слияния, закрытия и протоколы не создаются.
