# Организация Scrum-процесса

## Роли и ответственность

Product Owner упорядочивает Product Backlog, согласует цель продукта и проверяет пользовательскую ценность. Scrum Master помогает соблюдать Scrum и устранять препятствия, не распределяя работу вместо разработчиков. Developers оценивают и выбирают работу, создают проверяемый Increment и отвечают за качество.

Это организационная модель, а не перечень нанятых участников. В учебном проекте автор Критский С. Д. может совмещать обязанности; фактическая команда не выдумывается. Персоны POA не назначаются исполнителями. Assignees заполняются только при согласованном принятии задачи.

## Артефакты и обязательства

Product Backlog состоит из реальных Issues: Epic → PBI → Task. Epic группирует направление, PBI описывает ценность, Task фиксирует техническую часть. Все элементы входят в существующий GitHub Project. Product Goal: пользователь воспроизводимо проводит полный локальный эксперимент и сравнивает результаты разных реализаций.

Sprint Backlog включает выбранные PBI, технические Task и план достижения Sprint Goal. Поле Iteration определяет принадлежность спринту. Назначение спринта означает план, а не выполненную разработку.

Increment должен удовлетворять Definition of Done. Закрытый Issue, красивый макет или заполненная таблица не заменяют работающий проверенный результат.

## События

- Sprint: две недели. Даты существующего шаблона сохранены; восемь итераций MVP описаны в [плане](Sprint-Planning.md).
- Sprint Planning: выбрать цель, проверить зависимости, уточнить критерии и оценки, согласовать объём с доступностью разработчика. Показатели 13–22 SP являются предварительным разбиением, а не измеренной velocity.
- Daily Scrum: коротко проверить продвижение к цели, план на ближайший день и препятствия. При индивидуальной работе вести краткую запись по реальной работе, не сочинять протоколы состоявшихся встреч.
- Sprint Review: показать работающий сценарий и доказательства критериев, получить обратную связь и переупорядочить Product Backlog.
- Sprint Retrospective: оценить процесс, проверки и препятствия; выбрать одно конкретное улучшение следующего спринта.

Встречи в этой работе не объявляются проведёнными. Праздничные дни и загрузка автора, особенно на рубеже года, учитываются при уточнении плана.

## Definition of Ready

История содержит роль, ценность, границы, проверяемые критерии, приоритет и релиз; зависимости понятны, размер допускает завершение в спринте, оценка обсуждена. Для работы определены проверочные данные и необходимые средства. Техническая Task имеет одного родителя и конкретный проверяемый результат.

До фактического Sprint Planning элементы остаются в Backlog. Переход в Ready выполняется после подтверждения этих условий, а не автоматически по назначению даты.

## Definition of Done

- Реализованы все критерии приёмки в согласованной границе Issue.
- Пройдены подходящие модульные, интеграционные и сценарные проверки; для вычислений проверена правильность, а не только сборка.
- Обработаны ошибки и отмена; нет известных блокирующих дефектов.
- Выполнены Review или явно обозначенная самопроверка; результат принят ответственным за продукт.
- Документация обновлена, изменения находятся в `main`, есть связи с Issue и подтверждение проверок.

Для Epic требуются принятые дочерние PBI всех заявленных релизов. Завершение части MVP не закрывает направление Version 1/2.

## Статусы

| Переход | Условие |
| --- | --- |
| Backlog → Ready | Подтверждены Definition of Ready и включение в ближайший план |
| Ready → In Progress | Исполнитель принял задачу и реально начал работу |
| In Progress → In Review | Есть результат, проверки и ссылка на PR либо иной проверяемый артефакт |
| In Review → Done | Выполнены критерии, Review и Definition of Done |
| In Review → In Progress | Найдены замечания, требующие исправления |
| Done → Backlog/Ready | При переоткрытии пересмотрены критерии и причина возврата |

Создание GitHub-инфраструктуры не делает функциональные PBI выполненными. Все истории и Task первоначально остаются открытыми; им не назначаются фиктивные статусы In Progress/Done.

## Автоматизация и контроль

Авто-добавление относится только к Issues этого репозитория. Закрытие Issue может отражаться статусом Done только при соблюдении правил закрытия. Связь PR с Issue не является доказательством завершения. Ключевое слово `Closes` допустимо только для полностью реализованного Issue, `Refs` применяется для частичного вклада.

Автоархивирование не требуется для нового учебного бэклога: завершённые результаты должны оставаться видимыми для проверки. Фактические включённые workflows и ограничения перечислены в [конфигурации](Project-Configuration.md).
