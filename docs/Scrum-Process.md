# Организация Scrum

## Роли

Владелец продукта упорядочивает бэклог и принимает результат. Scrum-мастер помогает соблюдать процесс и устранять препятствия. Разработчики оценивают работу, выбирают объём спринта и реализуют функции. При индивидуальной работе автор проекта совмещает эти обязанности. Исполнитель указывается в поле Assignees, когда берёт задачу в работу.

## Материалы Scrum-проекта

Цель продукта: пользователь проводит воспроизводимый локальный эксперимент и корректно сравнивает реализации. Задачи в GitHub организованы по схеме: функциональный раздел → пользовательская история → техническая задача. Бэклог спринта включает выбранные истории, технические задачи и план достижения цели. Распределение хранится в поле «Спринт». Результат принимается по критериям задачи: для макета проверяются экраны и переходы, для реализации функции проверяется её работа.

## События

- Спринт: две недели, всего 13 предварительных интервалов. Цели, состав, зависимости и результаты указаны в [плане](Sprint-Planning.md).
- Планирование спринта: проверить зависимости, открытые вопросы, тестовые данные, доступность исполнителя и объём работы. Оценки отражают сложность задач, а не количество дней.
- Ежедневное обсуждение: продвижение к цели, ближайший шаг и препятствия. При индивидуальной работе допустима краткая запись по фактической работе.
- Обзор спринта: показать результат и пройденные проверки, собрать замечания и уточнить бэклог.
- Ретроспектива: анализ процесса и выбор конкретного улучшения.

Даты и состав спринтов уточняются с учётом загрузки и праздничных дней.

## Условия готовности задачи к разработке

Понятны роль, ценность и границы, есть конкретные требования, входы и выходы, сценарии и ошибки, проверяемые критерии, приоритет, выпуск, оценка и зависимости. Существенные открытые вопросы согласованы, проверочные данные определены. Размер позволяет завершить работу в спринте. Техническая часть имеет одного родителя и конкретный результат.

Для задач CUDA сначала нужно выбрать транслятор и описать его ограничения. Для анализа производительности нужно согласовать методику измерений. После этого соответствующую задачу можно перевести в «Готово к работе».

## Условия завершения задачи

- Реализованы все согласованные критерии в пределах выпуска.
- Пройдены подходящие модульные, интеграционные и пользовательские проверки; вычисление проверено на эталоне.
- Ошибки и отмена обрабатываются явно, данные не теряются, нет блокирующих дефектов.
- Выполнена проверка кода или явно обозначенная самопроверка; результат принят ответственным за продукт.
- Документация и связи с задачами обновлены; изменения находятся в основной ветке, результаты проверок приложены к запросу на слияние.

Функциональный раздел не закрывается по одной технической задаче или только по части первого выпуска: будущие дочерние функции остаются открытыми.

## Статусы и переходы

| Переход | Условие |
| --- | --- |
| Бэклог → Готово к работе | Подтверждены условия готовности и ближайший план |
| Готово к работе → В работе | Работа фактически начата |
| В работе → На проверке | Есть проверяемый результат, проверки и связь с изменениями |
| На проверке → Выполнено | Выполнены критерии, проверка и условия завершения |
| На проверке → В работе | Есть замечания для исправления |
| Выполнено → Бэклог | Issue переоткрыта, причина и критерии пересмотрены |

## Автоматизация

В проекте включены восемь правил автоматизации. Новые открытые задачи этого репозитория и дочерние задачи добавляются на доску. Связанный запрос на слияние переводит задачу в работу. Команда `Closes #N` закрывает полностью выполненную задачу, а `Refs #N` связывает с ней частичное изменение. Родительская история закрывается после выполнения всех её критериев, а не одной технической задачи.
