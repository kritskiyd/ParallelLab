# Проектная архитектура

Архитектура разделяет работу с экспериментом, выполнение программ, хранение результатов и анализ. Интерфейс разрабатывается на основе существующего прототипа.

## Объекты и ответственность

Эксперимент содержит идентификатор, название, описание, реализации и настройки по умолчанию. Реализация описывает технологию и набор исходных файлов. Сохранённая запись запуска ссылается на эксперимент, но хранит зафиксированную ревизию исходного кода и собственные снимки параметров и окружения.

Редактирование эксперимента не меняет уже полученное измерение. Серия содержит план конфигураций и ссылки на отдельные запуски. Производные аналитические представления строятся по сохранённым записям, а не по текущим значениям полей интерфейса.

## Модули

| Модуль | Ответственность | Граница |
| --- | --- | --- |
| Рабочая область | Навигация, дерево файлов, редактор, параметры, консоль | Отвечает за интерфейс и команды пользователя |
| Управление экспериментом | Формат, проверка и локальное хранение | Не смешивает текущее состояние и результаты прошлых запусков |
| Адаптеры технологий | Команды сборки и запуска, доступные параметры | Sequential, OpenMP, MPI и CUDA-транслятор имеют явные профили |
| Диагностика | Проверка инструментов, версий и причин недоступности | Отсутствие GPU не блокирует независимые CPU-режимы |
| Управление выполнением | Дочерние процессы, вывод, отмена и состояние | Получает вывод и статус от запущенного процесса |
| Серии | План конфигураций, повторы и прогресс | Один результат на одно фактическое выполнение |
| Хранилище результатов | Код/ревизия, условия, статус, время и результат | Старые записи не переписываются при изменении настроек |
| Аналитика | Проверка сопоставимости, таблицы и графики | Не интерпретирует CPU-транслятор как измерение GPU |

## Конвейеры выполнения

Sequential/OpenMP/MPI: проверка параметров и окружения → фиксация ревизии → сборка → выполнение → проверка результата → сохранение записи.

CUDA-транслятор в MVP: проверка поддерживаемых конструкций → преобразование в C++17 → CPU-сборка → CPU-выполнение → проверка → сохранение режима и условий. Неподдерживаемая конструкция завершается диагностикой.

CUDA Native во втором выпуске: проверка GPU, драйвера и CUDA Toolkit → сборка CUDA Native → GPU-выполнение → проверка → сохранение GPU и методики измерения. Этот путь не требуется для готовности MVP.

## Зависимости и риски

Для выполнения программ нужны локальные компиляторы и среды выполнения. Различия платформ и поддерживаемое подмножество CUDA требуют отдельных проверок. Сначала реализуется локальное выполнение. Удалённые профили, контроль доступа и передача данных относятся к третьему выпуску.

Стек интерфейса, формат хранения и способ изоляции выполнения нужно согласовать до реализации соответствующих компонентов. Эти решения описываются в задачах вместе с ограничениями и способом проверки.
