# Руководство разработчика

## Начало работы

Репозиторий уже создан и клонирован. Повторное создание GitHub Repository или Project не требуется. Оригинальные документы предыдущих лабораторных не изменяются.

```sh
git clone https://github.com/kritskiyd/ParallelLab
cd ParallelLab
git status
```

Эти команды нужны новому участнику; повторно выполнять clone внутри существующей рабочей копии нельзя. Для приватного репозитория используется стандартный разрешённый вход GitHub. Токены не хранятся в документации, скриптах и адресе remote.

## Порядок разработки

1. Прочитать [требования](Requirements.md) и [границы архитектуры](Architecture.md).
2. Выбрать Ready Issue ближайшего спринта, согласовать назначение и цель.
3. Создать рабочую ветку по [правилам](../CONTRIBUTING.md).
4. Реализовать только согласованную функцию, добавить проверки.
5. Открыть PR с `Refs #N` либо обоснованным `Closes #N` и результатами тестов.
6. После Review и проверки критериев обновить Issue и документацию.

## Вычислительное окружение

MVP требует C++17 toolchain; для OpenMP нужна его поддержка, для MPI соответствующий runtime и средство запуска. CUDA-транслятор имеет явно документируемое поддерживаемое подмножество и собственные CPU-зависимости. Конкретные версии и платформы будут зафиксированы при реализации и проверке адаптеров.

CUDA Native добавляется в Version 1 и требует совместимого оборудования NVIDIA и CUDA Toolkit. В MVP нельзя блокировать CPU-режим только из-за отсутствия такого оборудования.

## Проверки

Сначала проверяются известные результаты маленьких задач. Затем сравниваются несколько реализаций с одинаковыми данными. Сохраняются ревизия, параметры, режим и снимок системы. Неподдерживаемые CUDA-конструкции не должны молча пропускаться. Запуски проверяются на ошибку компиляции, ошибку выполнения, отмену, недоступный инструмент и невозможность сохранить результат.

Команды сборки и запуска продукта пока не приведены, потому что исходного исполняемого приложения в этом репозитории нет. Фиктивные `npm test`, сборки или отчёты о прошедших тестах не создаются.

## Документация и синхронизация

При изменении PBI синхронизируются критерии, milestone релиза, Priority/Release/Story Points/Iteration в Project и соответствующие метки. Числовое поле принимает любую числовую величину, поэтому допустимая шкала 1, 2, 3, 5, 8, 13 контролируется на Planning и Review, а не объявляется технически запрещённой для других чисел.
